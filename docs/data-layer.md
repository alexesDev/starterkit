# Data layer

SQLite in WAL mode, queries generated by [sqlc](https://sqlc.dev), migrations by
[dbmate](https://github.com/amacneil/dbmate). No ORM, no query builder — the SQL
you write is the SQL that runs.

## The read/write split

`queries.read.sql` holds every `select`. `queries.write.sql` holds every
`insert`/`update`/`delete`. sqlc generates both onto the same `*Queries`
receiver, and then `make sqlc` runs `internal/db/fix_write_queries.sh`, which
rewrites the write file's receiver to `*WriteQueries`:

```go
type WriteQueries struct {
	*Queries
}
```

The result: `db.Queries` (built on the read pool) exposes only reads.
`db.WriteQueries` (built on the write pool) exposes both. A function holding a
read handle **cannot** write — that is a compile error, not a code review note.

`make lint` runs `internal/db/list_queries.sh`, which fails if a write statement
appears in the read file or a top-level `select` in the write file. The compiler
enforces the split *after* a query is filed correctly; that script is what
catches misfiling. It also enforces the query naming rule and the timestamp
rule below.

> Run `make sqlc`, never bare `sqlc generate` — the raw command leaves the write
> methods on `*Queries` and quietly dissolves the split.

## Three connection pools, one file

`internal/db/setup.go` opens:

| Pool | Max conns | For |
|---|---|---|
| Read | 25 | everything that only selects |
| Write | **1** | write transactions |
| Queue | 1 | goqite polling, kept off the app's write pool |

The write pool is capped at one on purpose: SQLite has exactly one writer, so
more connections would only add contention.

The queue's own pool keeps polling from queuing behind application writes *for a
connection*. It does not make the two independent at the database level: SQLite
still has a single write lock, so a poll can wait behind an open application
transaction. Separate pools, shared lock.

Every pragma goes through the DSN, not `db.Exec`:

```go
q.Add("_pragma", "busy_timeout(20000)")
q.Add("_pragma", "journal_mode(WAL)")
q.Add("_pragma", "foreign_keys(1)")
q.Add("_pragma", "synchronous(NORMAL)")
q.Set("_txlock", "immediate")   // writers only
```

This matters more than it looks. `PRAGMA foo` executed through `db.Exec` only
configures whichever pooled connection happened to run it, leaving the rest at
SQLite defaults — `busy_timeout=0` and **foreign keys off**. Via the DSN the
driver applies them to every connection it opens.

`_txlock=immediate` is the other non-obvious one. A deferred transaction begins
as a reader and upgrades on first write; if another connection committed in
between, the upgrade fails instantly with `SQLITE_BUSY_SNAPSHOT`, and
`busy_timeout` cannot help because the snapshot is already stale. Immediate mode
takes the write lock at `BEGIN`, so writers queue instead of failing.

The read pool also carries `query_only(1)`. That is a second, independent wall
under the compile-time split: even a mistake that reached this pool with a write
could not execute it.

## Timestamps

Every time column is `integer` unix seconds in a `STRICT` table, and a sqlc
`overrides` entry maps it to `dbtime.Stamp`. The measurement behind that choice,
the two traps it has, and the build check that keeps it true are in
[rules.md](rules.md). What matters here:

- `sqlc.yaml` uses wildcard overrides (`column: "*.created_at"`), so it is a few
  lines rather than one per table. A wildcard is schema-wide, which is why the
  schema has to be uniform.
- Nullable time columns need their own entry with `nullable: true` and
  `pointer: true` inside `go_type`; they generate `*dbtime.Stamp`.
- `internal/db/list_queries.sh` fails the build when a column ending in `_at` or
  `_date` is not `integer`, has no override, or lives in a table that is not
  STRICT.
- The columns are written by the application, not defaulted, so `app.Now()` is
  the one clock and a case that stores a time declares `Now()` on its `Env`.
- `emit_pointers_for_null_types: true` is on, so nothing in `internal/db` is a
  `sql.NullString`.

The queue's table is the single place holding text timestamps. It is goqite's
own schema, vendored verbatim, and its columns are named `created`, `updated`
and `timeout` — outside our `_at`/`_date` convention, so no override matches
them and nothing in Go reads them.

## Migrations

```bash
make db-new name=add_widgets   # creates db/migrations/<timestamp>_add_widgets.sql
make db-up                     # applies, then regenerates db/schema.sql
make db-down                   # rolls back the last one
make db-status
```

Format is dbmate's:

```sql
-- migrate:up
create table widgets (
  id integer primary key autoincrement,
  created_at integer not null
) strict;

-- migrate:down
drop table widgets;
```

`db/schema.sql` is a **build artifact** regenerated on every `db-up`. Never edit
it. sqlc reads it as its schema input, which is why `make db-up` has to come
before `make sqlc`.

The server also migrates itself on boot from the embedded `db/migrations`
(`db/embed.go`), so a deploy needs no separate migration step.

## One DATABASE_URL, two consumers

`.env` carries a single `DATABASE_URL=sqlite:data.sqlite3`. dbmate reads it, and
so does `internal/appconfig` — deliberately the same setting, so `make db-up`
and the server's migrate-on-boot cannot end up pointing at different files.

## cgo, and where it is allowed

dbmate's own sqlite driver sits behind a `cgo` build tag because it imports
`mattn/go-sqlite3`. That is fine for `make db-*`, which runs on a developer
machine that has a C toolchain.

The **server** must not need one: `CGO_ENABLED=0` is what makes the binary
static. So `internal/dbmate/sqlite` re-registers dbmate's driver against
`modernc.org/sqlite`, and `internal/db.Migrate` uses that with the embedded
migrations at boot. Same migrations, same file, no C compiler in the image.

`make db-up` also shells out to the `sqlite3` binary to dump `db/schema.sql`.
Dev-time only — the server never dumps.

## Query style

```sql
-- name: DBGetUserByID :one
select * from users where id = ?;

-- name: DBListAuditLog :many
select * from audit_log
 where (id < sqlc.arg(before) or sqlc.arg(before) = 0)
 order by id desc
 limit sqlc.arg(page_limit);
```

Lowercase keywords. Positional `?` for simple cases, `sqlc.arg(name)` when a
parameter is used twice or needs a readable name.

Keep SQL comments **ASCII**. A single multi-byte character — an em dash is the
easy way to do it by accident — shifts sqlc's byte offsets when it rewrites a
query, and it fails with something like `extraneous input 'selecuser_id'`
pointing at an unrelated line.

One gotcha on `sqlc.arg`: sqlc infers a parameter's Go type from its first use.
`where (sqlc.arg(before) = 0 or id < sqlc.arg(before))` infers `interface{}`
from the comparison against a literal; putting the column comparison first —
`where (id < sqlc.arg(before) or sqlc.arg(before) = 0)` — infers `int64`.

## Pagination

The audit log uses keyset pagination, which is the right default for an
append-only table:

```graphql
auditLog(limit: 50, before: 1234) {
  totalCount
  nodes { id action email createdAt { formatted(layout: "2006-01-02 15:04:05") } }
  pageInfo { hasNextPage endCursor }
}
```

`id` is autoincrement, so `order by id desc` is `created_at desc` without the
ties a second-granularity timestamp produces. Pass the previous page's
`endCursor` back as `before`. The case fetches `limit + 1` rows and trims the
extra one — that is how `hasNextPage` is known without a second query.

Offset pagination would let the UI jump to page N, at the cost of scanning at
depth and shifting rows under the reader whenever a new entry lands. For a log
that is written to constantly, keyset is the honest choice.
